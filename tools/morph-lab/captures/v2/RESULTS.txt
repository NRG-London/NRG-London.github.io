SPIKE-VERDICT: deck.gl's built-in transitions NEGATIVE; the CPU path POSITIVE

  NEGATIVE — `transitions: {getPolygon}` does not animate the outlines. It stops
  the SolidPolygonLayer drawing at all: ink 0.0363 against the control's 0.3166,
  17.00/255 away from it, identical under Float32 (ink 0.0363) because the layer
  declares its own attribute type as float64 whatever array is handed in. The
  mechanism, from the browser rather than from inference:
      WebGL: INVALID_OPERATION: beginTransformFeedback: not enough transform feedback buffers bound
      WebGL: INVALID_OPERATION: endTransformFeedback: transform feedback is not active
  deck.gl runs an attribute transition as a transform feedback pass and cannot
  bind the buffers for SolidPolygonLayer's double-precision vertexPositions. It
  is SILENT: the page's own error count stayed at 0 throughout, because a WebGL
  INVALID_OPERATION is not a JavaScript exception. Reproduce with ?postrans=1.

  POSITIVE — driving the same warp from requestAnimationFrame does animate it:
  8.35% -> 54.05% -> 94.82% across a 3000 ms ease, at 40.9 fps (24.2 ms ema, 38.9 ms
  worst) with 689 features and 50,738 vertices re-warped, re-uploaded and
  re-tessellated every frame. deck.gl draws swapped-in positions exactly — S4
  above puts an in-place swap 0.0006/255 from a first draw of the same geometry.

  WHAT THE CPU PATH CANNOT DO is carry the VALUES at the same time. Any attribute
  deck.gl holds in transition is drawn from the transition's own buffer, so one
  handed a new value every frame is superseded before it lands, and leaving the
  values on deck's transition while the outlines move restarts that transition
  sixty times a second. S6 above measures exactly that, live, this run: at the
  83% mark of the ease the values are 29.14% of the way across, where a working
  transition would be at ~96.6%. They arrive only once the loop stops restarting
  them (0.0005/255 from the ward map by then), which is after the animation has
  finished — so the motion is wrong even though the destination is right.

  Two further arms were measured in separate probe runs during development and
  are NOT re-measured here — see task-4-report.md §3 of the continuation for both:
    * values lerped on the CPU and handed over per frame never arrive at all
      (0.01% of the way across at u = 0.64, at every duration from 1 ms to 750 ms).
    * taking the values out of `transitions` altogether blanks the layer the
      moment a vertex moves.
  So the choreography gives the outlines and the values SEPARATE BEATS, and every
  beat runs on a mechanism with proof.
