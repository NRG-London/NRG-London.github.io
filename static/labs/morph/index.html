Geography-morph workbench

This is a temporary prototype workbench for morphing between geography levels on the census map.

STATUS — 2026-08-17. Both prototypes have shipped; this workbench is no longer the decision. v1's value-morph went to production on 2026-08-16, and v3 is production as of 2026-08-17 (shortcode ?v=11, build 425f758b6f) — every area-type change on the live census map is now the one-gesture crack morph. Both the shipped page and v3 below carry per-tier crack insets — oa .80, lsoa and ward .92, borough .96 — because the gap a crack opens is proportional to the ring it opens around, so a single scalar cracked boroughs open and left output areas barely moving. What did not ship with it: the CPU reference warp, the staged references, the DOM scrubber, the shader A/B and the per-pair query override, on the principle that a production page does not get a second code path so that a test can photograph something. Those levers still exist here, which is most of why this page is still standing. The workbench is retained temporarily for the post-launch watch (the eye checklists below are still the fastest way to put a specific question to a real machine); teardown is planned in a few days.

  • v0/ — minimal harness: split/merge value-morph on the OA basis (buttons, duration/easing controls, HUD)
  • v1/ — SHIPPED 2026-08-16 (?v=10). Full census map with the curtain replaced by the morph (?morph=0 restores the curtain; ?hud=1 overlay). Production has since moved on to v3's warp, which is v1's morph with the crack added — ?warp=0 on the live page is this.
  • v2/ — boundary-warp experiment: wards crack apart out of a borough block and heal back. Two verdicts. deck.gl's own transitions cannot tween getPolygon here — declaring one blanks the layer outright, silently (?postrans=1 reproduces it). Driving the warp from requestAnimationFrame instead does animate it, at ~25–46 fps. Outlines and values cannot move at the same time, so each choreography plays them as separate beats. Stills of the crack: ?s0=0.92, ?s0=0.8. Numbers in tools/morph-lab/captures/v2/RESULTS.txt.
  • v3/ — SHIPPED 2026-08-17 (?v=11, build 425f758b6f). The warp on the GPU, and v2's three beats collapse into one. A custom deck.LayerExtension adds one per-vertex ring-centroid attribute and one morphT uniform and injects at vs:DECKGL_FILTER_GL_POSITION; the position attribute deck.gl blanked on is never written after the first draw, so there is no re-tessellation, and the value transition runs concurrently with the crack. Measured across runs — the evidence regenerates on every driver run, so these are ranges rather than one run's readings: the values ~30–31% across at a ~99.8% crack, in the same frame, where v2's CPU path left them at 29.25% by the 84% mark; ~90–180 fps against v2's 34–46, on a machine that is not a clean room; the shader warp ≤0.0034/255 from a CPU warp of the same geometry; and the extension at rest ≤0.0001/255 from the page built without it. Now the whole transition policy, not one pair: a table with a line per ordered pair cracks the finer tier of a nested pair — wards, boroughs, LSOAs or the 26,435 output-area rings, including the zoom auto-switch — and shatters a non-nested one city-wide on the output areas. Thirteen of the thirty are photographed end to end — all three modes, all four cracking geometries — and every one lands on the map a direct load draws, ≤0.002/255 across runs against a limit of 2.0. The committed run's own figures are in RESULTS.txt. ?warp=0 is V1 exactly; ?bench=1 scrubs the uniform by hand. Numbers in tools/morph-lab/captures/v3/RESULTS.txt.

Driving guide

The three prototypes are built and self-verified, and the aesthetic calls they were built to put to a human eye have now been made and shipped — v1 on 2026-08-16, v3 on 2026-08-17. What is left is the post-launch watch: drive each page from the links below and work the checklist underneath when something on the live map looks wrong and you want to isolate it against a machine you control.

v0 — minimal harness

Buttons, duration, and easing controls over a bare split/merge value-morph on the OA basis.

Morph proven to slide, not snap: mid-flight progression 33.8% → 73.3% → 98.0%, endpoints land ≤1 px off, plateau (OA painted with borough values vs. the true borough map) MAD 0.045/255.

Zooming mid-morph in v0 (only) restarts the transition — v0 predates the polyData fix that v1 carries. Judge that behaviour in v1, not v0.

v2 — boundary warp, ward↔borough

Wards crack apart out of a borough block and heal back, instead of a value-only morph.

deck.gl's built-in position transitions BLANK the layer outright (repro preserved at ?postrans=1). The CPU-driven warp works instead: ~25–46 fps, but outlines and values can't move together, so the choreography plays as three separate beats (crack → values → heal).

v3 — the warp on the GPU, as one gesture (shipped 2026-08-17)

The same crack-and-heal as v2, but the displacement happens in the vertex shader, so the values can move while the seams are open. Every area-type change is now one continuous gesture, under a single policy table with a line per ordered pair: a nested pair cracks the finer tier of the two (wards out of a borough, output areas out of a neighbourhood — including the zoom auto-switch at 12.6), and a pair that does not nest shatters the whole city along output-area boundaries while the values flow, because that is the geometry V1 was already drawing it on. One line of the table demotes any pair back to the plain morph.

Spike verdict POSITIVE. Injection point: vs:DECKGL_FILTER_GL_POSITION — the only one of deck.gl's four declared hooks that can reach position. Concurrency proven against staged references carrying the same crack: at the envelope's peak the geometry is ~99.8% displaced and the values are ~30–31% across in that same frame, where v2's CPU path left them at 29.25% by the 84% mark. Endpoints ≤0.0004/255 on the split and 0.0000/255 on the merge; zero WebGL errors anywhere; every committed frame passes an ink gate, because v2 spent a sprint with a blank map and a clean error count.

Frame rate at ward grain has measured ~90–180 fps for the scrub and ~140–180 for the gesture, against v2's 34–46; at output-area grain — 26,435 rings cracking at once — the same gesture has measured ~60–170. Both ends of those ranges are runs of identical code on a machine that is not a clean room, and the state and pixel gates do not move between them. Across runs the worst frame has ranged 8.4–75 ms, so the mean hides a spike that has not been chased down; headless Chrome does not lock rAF to vsync either, so none of these is a 60 Hz claim. Read the report's concerns.

The table is read back off the page and checked line by line, and thirteen of the thirty pairs are then photographed end to end — cracking wards, boroughs, LSOAs and output areas, shattering two non-nested pairs, and one pair demoted by hand to prove the lever — each against a direct load, ≤0.002/255 across runs. All ten nested crosswalks are composed through oa.parents.json and throw rather than approximate: 689 of 689 wards, 4,994 of 4,994 LSOAs, 26,369 of 26,369 output areas, no conflicts. Interrupts are gated on an idle read-back over every resident tier, because a crack left frozen on one is a defect no endpoint can see.

?warp=0 takes the extension out entirely and is asserted pixel-identical to v1 on the same route. ?warpmode=ward>pcon:none demotes one pair to the plain morph, which is the same lever the table carries. ?bench=1 puts a slider straight onto the uniform. ?cpuwarp=0.92 is the CPU ground truth the shader is measured against; ?stage=plateau holds the ward layer at the borough plateau.
